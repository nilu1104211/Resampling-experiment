## 8. 比较之前必须核对的口径

1. 同一个数据集和条件内，对象集合、sample ID、GT 和输入数据对应；不能只凭“都是 80 个”判断相同。
2. 主表只比较共同的 2048→8192 整物体结果；局部 256→1024、验证集监控或 smoke 结果分开。
3. 所有距离统一到公共 canonical 坐标；CD-L1、平方 CD、HD、F-score 的定义和阈值一致。
4. 使用何种末尾权重/验证选模规则要明确，不能将 `last.pt` 自动叫作 best。
5. 原版与加速版推理分别记录，核对 FPS、批处理、步数、归一化、分块/合并、时间表和后处理。代码总哈希会因为新增 Ours 入口发生变化，不能只凭总哈希不同就宣布结果不可比；应核对具体评价与推理差异。
6. SPU 保持自监督，其内部目标与监督方法不同；相同输入不代表相同训练损失。Ours 的辅助退化标签、教师和额外训练成本应披露。
7. 速度统一硬件、计时范围、预热及 GPU 并发状态；从预测 JSON 汇总实际计时，不把训练耗时、指标耗时与模型预测混在一起。

建议质量表先按 **模型 × 数据集 × 条件** 展示，再做预先说明的汇总。不要默默对不同条件数量或不同覆盖率的结果取总平均。

主要字段：

| 指标 | 方向 |
| --- | --- |
| `cd_l1` | 越小越好 |
| `cd_l2_squared` | 越小越好，注意是平方距离 |
| `hausdorff_l2` | 越小越好 |
| `f_score` | 越大越好；当前公共评价默认阈值 0.01 |
| `hole_coverage_mean_l2` / `sparse_coverage_mean_l2` | 越小越好，适用于有对应区域的样本 |
| `hole_coverage_fraction` / `sparse_coverage_fraction` | 越大越好，适用于有对应区域的样本 |
| `p2f_mean_l2` 等 | 仅在确实计算并具备共同网格口径时比较 |

不要比较有物理尺度差异或手工乘不同倍数的数值。若展示 ×1000 等尺度，所有模型使用同一列单位，并保留原值。

- 局部最终输出 1024 点，整物体通过内部块预测/合并最终 8192 点。
- `native` 只保留历史推理参考，**禁止用它进行当前主对比训练**。先前曾误引入额外 1024 点训练输入，已撤回并删除额外输入池 API。
- `legacy-patch256` 是旧权重兼容模式，不能与当前 shared-v3 权重混用。
- 这仍属于明确的 V3 数据适配，不能宣称原论文完整复现或保证原方法质量完全不变。

### 9.4 尚未解决但不阻止当前结果收集的研究问题

- 目前 PUFM/Ours 从局部训练迁移到整物体直接积分，与保留的正式 PUFM 局部分块评测入口不同；本轮只补 Ours 加载和公共评价，没有改推理算法。
- 当前 PUFM++ 适配的固定观测块/局部积分，与保留的原评测逐时间步从整云取块流程存在差异。近期 CUDA FPS 加速保留当前适配定义，并未解决这项方法差异。
- MGB 需要留出样本的实际分配收益证明；现有 `evaluate-gain` 主要抽查统一配额附近的交换，不等同于完整迭代分配评测。
- 核心消融应包括基线、仅 RGR、仅 MGB、RGR + MGB。当前不要先因静态差异宣布已有权重无效，也不要为了让结果更好立即加模块或根据测试集调参。

这些问题应在比较解释中披露，并作为后续独立验证工作，不要把当前任务擅自改成重新设计/重训。
